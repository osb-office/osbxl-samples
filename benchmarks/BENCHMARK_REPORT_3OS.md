## 1. まとめ

### 💡 結論を一言でいうと
> **「従来の Excel ライブラリでサーバーが落ちていた 5 万件の大規模帳票が、osbxl ならわずか 0.6 〜 0.9 秒・メモリ数十MBで安全に完走します」**  
> 日常的な Web API 帳票（200行）ならわずか **7〜10 ミリ秒（0.007秒）**。ユーザーを一切待たせません。

---

### 📌 なぜ今、この検証を行ったのか？（背景と課題）
Web システムの帳票ダウンロードや夜間バッチ処理において、長年エンジニアを悩ませてきたのが次の 2 大トラブルです：
1. **「データ件数が増えるとメモリ不足（OOM）でサーバープロセスが即死する」**
2. **「書き出しに何十秒もかかり、Web サーバーがタイムアウトを起こす」**

そこで本検証では、日常帳票（100〜1,000行）から限界バッチ（50,000行 / 200,000セル＋SUM計算）まで、**主要 4 言語（PHP, Python, Node.js, Java）** と **実務の代表的な 3 大プラットフォーム（クラウド GCP C3/C4、Mac M4、Windows 11）** を網羅し、同一データ・最新ランタイム条件での徹底的な実測比較を行いました。

---

### 🏆 実測から判明した「3 つの決定的な事実」

#### ① 【メモリクラッシュの根絶】50,000 件でもプロセスが絶対に落ちない
* **従来の既存ライブラリ（PHP: PhpSpreadsheet / Java: Apache POI）**:  
  一般的なクラウドやコンテナの標準設定（メモリ上限 256MB）では、50,000 行に達した瞬間にヒープを使い果たし、**確実に OOM（プロセス強制終了）で即死** します。
* **osbxl**:  
  C++ ネイティブコアが直接ストリーム処理を行うため、言語側のヒープ消費は **わずか 30MB〜64MB のまま一定**。全環境・全言語で **0.6 秒〜 0.9 秒台で余裕の安全完走** を果たしました。  
  👉 *「帳票ダウンロードのために Web サーバーのメモリ上限を何ギガも引き上げる」必要はもうありません。*

#### ② 【日常の Web レスポンスが爆速化】200 件の帳票ならわずか 7 ミリ秒
* 画面から「ダウンロード」ボタンを押して即座に出力されるような日常帳票（200行 / 800セル）において、PHP・Python・Node.js ともに **0.007 〜 0.008 秒（7〜8ms）** でファイル生成を完了します。
* Java においても、Apache POI で 0.5 秒以上かかっていた巨大クラス構造の初期化遅延を解消し、**0.1 秒** でレスポンスを返します。  
  👉 *ユーザーを待たせる待ち時間はゼロになり、タイムアウトのリスクも完全に解消されます。*

#### ③ 【クラウド世代進化】最新 GCP C4 は C3 比で 10%〜30% のスループット向上
* クラウドサーバー選定において、GCP の第4世代 Xeon（C3: Sapphire Rapids）と最新第5世代 Xeon（C4: Emerald Rapids）を同一 4 vCPU・同一条件の下で比較検証しました。
* **C4 は全言語で C3 より 10%〜30% 高速** を記録。10,000 行の帳票生成において、Node.js は **99ms（0.1秒切り）**、PHP は **0.101秒**、Java は **0.272秒** と、マイクロサービスや同時アクセス環境で圧倒的なスケーラビリティを発揮します。

## 5. アーキテクチャ考察：なぜ既存 OSS は落ち、osbxl は落ちないのか？

### ① 既存 OSS の限界：「言語ヒープ上のオブジェクト爆発」

PhpSpreadsheet、Apache POI (XSSF)、ExcelJS は、**「セル 1 つひとつを言語ランタイムのオブジェクトとして生成」** します。
- 50,000行 × 4列 ＝ **200,000 個のセルオブジェクト**
- さらに各セルが持つフォント、罫線、スタイル、数式定義オブジェクトが芋づる式に生成
- 保存時には共有文字列（Shared String Table）のハッシュマップがメモリを肥大化

その結果、出力される `.xlsx` ファイル自体はたかだか 1.5MB〜2MB 程度にもかかわらず、PHP では 256MB、Java では 256MB のヒープを瞬時に使い果たして異常終了します。

### ② osbxl の解決策：C++ ネイティブコアと 2次元配列一括投入

osbxl（各言語バインディング）では、言語側のヒープにセルオブジェクトを大量生成しません。
```javascript
// Node.js (nodeosbxl) での一括投入例
ws.setRangeData("A2", data);        // 2次元配列を生ポインタ経由で C++ ネイティブ層へ一括転送
ws.setRangeFormulas("D2", formulas); // 数式も 2次元配列で一括投入
```
1. 2次元配列として渡された生データを、言語ランタイムから **即座に C++ ネイティブメモリへ引き渡す**。
2. 最適化された C++ コアがストリーム処理で直接 OpenXML（ZIP / deflate）へ高速エンコード。
3. そのため、**Node.js の V8 ヒープは 20MB、Python ヒープは 28MB、PHP メモリは 32MB** のまま変動せず、言語ランタイムの OOM（ヒープ枯渇）クラッシュを根本から防止します。

### ③ サーバーサイドでの数式評価と SPILL（動的配列）対応

多くの OSS ライブラリ（openpyxl, ExcelJS）は数式文字列を書き込むことはできても、Excel 本体の計算機能を持たないため、サーバー上で数式結果（`SUM`, `VLOOKUP`, `XLOOKUP`）を取得できません。  
一方、**osbxl は「SPILL（スピル / 動的配列）形式の関数結果」に完全対応した最新の計算エンジン（約500関数）を内蔵**しています。Excel がインストールされていない Linux コンテナ環境でも、正確な計算結果を瞬時に取得可能です。

## 6. 導入推奨シナリオ

| シナリオ | 従来の課題 | osbxl 導入による効果 |
| :--- | :--- | :--- |
| **Web 帳票ダウンロード (100〜1,000行)** | 初期化遅延（POI は 0.5秒以上）、言語ごとの作法差 | **Java 4〜6倍、PHP 12〜14倍高速**。<br>全言語 0.01秒台で即時レスポンス。 |
| **月次バッチ・全件エクスポート (50,000行)** | メモリ上限超過（OOM）でプロセス即死 | **PHP・Java ともに 0.7秒〜0.9秒で安全完走**。<br>コンテナメモリ上限を気にする必要なし。 |

| **マルチ言語・マイクロサービス開発** | 言語ごとに別ライブラリ・別構文 | **Java / Python / Node / PHP / WASM で 100% 同一 API**。 |
