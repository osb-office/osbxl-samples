## 1. まとめ

### 💡 結論を一言でいうと
> **「従来の Excel ライブラリでサーバーが落ちていた 5 万件の大規模帳票が、osbxl ならわずか 0.3 〜 0.5 秒・メモリ数十MBで安全に完走します」**  
> 日常的な Web API 帳票（200〜1,000行）でも **6〜27 ミリ秒**。Java は Apache POI 比で **約23〜28倍**、PHP は **約7〜15倍**、Python / Node.js も **約2〜4倍** 高速です。

---

### 📌 なぜ今、この検証を行ったのか？（背景と課題）
Web システムの帳票ダウンロードや夜間バッチ処理において、長年エンジニアを悩ませてきたのが次の 2 大トラブルです：
1. **「データ件数が増えるとメモリ不足（OOM）でサーバープロセスが強制終了・クラッシュする」**
2. **「書き出しに何十秒もかかり、Web サーバーがタイムアウトを起こす」**

そこで本検証では、日常帳票（100〜1,000行）から限界バッチ（50,000行 / 200,000セル＋SUM計算）まで、**主要 4 言語（PHP, Python, Node.js, Java）** と **実務の代表的な 2 大プラットフォーム（Linux: クラウド GCP C3/C4、macOS: Apple M4）** を網羅し、同一データ・最新ランタイム条件での徹底的な実測比較を行いました。

---

### 🏆 実測から判明した「3 つの決定的な事実」

#### ① 【メモリクラッシュの根絶】50,000 件でもプロセスが絶対に落ちない
* **従来の既存ライブラリ（PHP: PhpSpreadsheet / Java: Apache POI）**:  
  一般的なクラウドやコンテナの標準設定（メモリ上限 256MB）では、50,000 行に達した瞬間にヒープを使い果たし、**確実に OOM（メモリ不足によるプロセス強制終了）で異常終了** します。
* **osbxl**:  
  C++ ネイティブコアが直接ストリーム処理を行うため、言語側のヒープ消費は **わずか 30MB〜64MB のまま一定**。全環境・全言語で **0.3 秒〜 0.5 秒台（C4）で余裕の安全完走** を果たしました。  
  👉 *「帳票ダウンロードのために Web サーバーのメモリ上限を何ギガも引き上げる」必要はもうありません。*

#### ② 【小さな帳票ほど「待たせない」】1,000 行以下の日常帳票でも全言語で高速（GCP C4 実測）
大規模バッチだけでなく、画面のダウンロードボタンで毎日何度も呼ばれる **100〜1,000 行の小さな帳票** こそ、体感速度に直結します。

| 行数 | PHP (PhpSpreadsheet → osbxl) | Python (openpyxl → osbxl) | Node.js (ExcelJS → osbxl) | Java (Apache POI → osbxl) |
| :--- | :---: | :---: | :---: | :---: |
| **200 行** | 0.016s → **0.006s** (2.5倍) | 0.012s → **0.007s** (1.6倍) | 0.009s → 0.009s (同等) | 0.503s → **0.018s** (**27.9倍**) |
| **500 行** | 0.156s → **0.010s** (**15.2倍**) | 0.022s → **0.010s** (2.1倍) | 0.025s → **0.008s** (3.3倍) | 0.563s → **0.021s** (**26.8倍**) |
| **1,000 行** | 0.070s → **0.010s** (**6.7倍**) | 0.033s → **0.011s** (3.1倍) | 0.039s → **0.010s** (3.8倍) | 0.628s → **0.027s** (**23.3倍**) |

* **Java は 0.5〜0.6 秒 → 20 ミリ秒台へ**: Apache POI は小さな帳票でも巨大な XMLBeans スキーマの初期化で毎回 0.5 秒以上かかります。osbxl は初期化負荷がほぼ無く、200 行で **約 28 倍**、1,000 行でも **約 23 倍** 高速です（macOS M4 でも 100〜200 行で約 30 倍）。
* **PHP は 500 行で 15 倍**: 1,000 行以下の領域で **6〜15 倍**、いずれも **10 ミリ秒前後** で応答します。
* **500 行以上は全言語で 2〜4 倍以上**。1,000 行では全 4 言語で **3 倍以上** の優位性があります。
* **しかも osbxl は数式計算エンジン・ピボット・暗号化などを標準搭載**。同じ速度を維持したまま、他ライブラリで不可能な機能が使えます。
* 補足（正直な評価）: 100〜200 行の Python / Node.js は既存ライブラリも数ミリ秒で完了するため差は小さく（200 行 Node.js は同等、100 行 Python は openpyxl が約 6ms 速い場合あり）、絶対時間の差は数 ms です。この領域の価値は速度よりも機能差と、規模が増えても劣化しない点にあります。

#### ③ 【クラウド世代進化】最新 GCP C4 は C3 比で約1.1〜1.4倍のスループット向上
* クラウドサーバー選定において、GCP の第4世代 Xeon（C3: Sapphire Rapids）と最新第5世代 Xeon（C4: Emerald Rapids）を同一 4 vCPU・同一条件の下で比較検証しました。
* **C4 は全言語で C3 より約1.1〜1.4倍高速** を記録。10,000 行の帳票生成において、Node.js は **56ms（0.056秒）**、PHP は **0.055秒**、Java は **0.208秒** と、マイクロサービスや同時アクセス環境で圧倒的なスケーラビリティを発揮します。

### ④ 言語別（4系統）代替ライブラリとの詳細対比と実務効果

#### [1] PHP 系: PhpSpreadsheet vs phposbxl
| 行数（データ規模） | PhpSpreadsheet (相手方) | phposbxl (True) | phposbxl (False) | 高速化倍率 (対相手方) |
| :--- | :---: | :---: | :---: | :---: |
| **500 行** | 0.156s | **0.010s** | 0.015s | **15.19 倍 高速** |
| **1,000 行** | 0.070s | **0.010s** | 0.017s | **6.73 倍 高速** |
| **5,000 行** | 0.357s | **0.032s** | 0.079s | **11.16 倍 高速** |
| **10,000 行** | 0.754s | **0.055s** | 0.157s | **13.60 倍 高速** |
| **50,000 行 (20万セル)** | ❌ **OOM (メモリ枯渇死)** | **0.355s** | 1.038s | **完走 (相手方OOM)** |

* **メモリ枯渇（OOM）の完全根絶**: PhpSpreadsheet はセルごとに巨大な PHP オブジェクトを生成するため、50,000行で 256MB を使い果たし Fatal Error (`Allowed memory size exhausted`) でサーバープロセスが即死します。phposbxl は C++ ネイティブコアが直接処理するため、PHP メモリ上限に関わらずわずか 20〜32MB・0.34秒で安全に完走します。
* **Web タイムアウトの解消**: 10,000 行をわずか **0.055 秒（約 14 倍高速）**、日常帳票（500〜1,000 行）を **11〜14 ミリ秒** で出力するため、並行ダウンロード時のキュー詰まりやタイムアウトを完全に解消します。
* **高度な機能完備**: PhpSpreadsheet に存在しないピボットテーブル作成機能や、約 500 関数の高速ネイティブ数式評価を標準装備しています。

#### [2] Python 系: openpyxl vs pyosbxl
| 行数（データ規模） | openpyxl (相手方) | pyosbxl (True) | pyosbxl (False) | 高速化倍率 (対 openpyxl) |
| :--- | :---: | :---: | :---: | :---: |
| **500 行** | 0.022s | **0.010s** | 0.015s | **2.09 倍 高速** |
| **1,000 行** | 0.033s | **0.011s** | 0.018s | **3.07 倍 高速** |
| **5,000 行** | 0.156s | **0.036s** | 0.081s | **4.40 倍 高速** |
| **10,000 行** | 0.311s | **0.063s** | 0.167s | **4.96 倍 高速** |
| **50,000 行 (20万セル)** | 1.604s | **0.389s** | 1.159s | **4.12 倍 高速** |

* **スループットが 3.5〜5.5 倍向上**: 行数が増えるほど openpyxl のオブジェクト生成遅延が累積しますが、pyosbxl は 50,000 行でも **0.37 秒台** で書き出しを完了します。
* **ヘッドレス数式評価エンジン内蔵**: openpyxl は Excel 本体の非起動下で数式再計算ができずセル値が `None` のままになります。pyosbxl は **約 500 関数の計算エンジンを内蔵** し、サーバー上で正確な計算結果を取得できます。
* **パスワード暗号化の標準対応**: openpyxl 単体では非対応のパスワード付き Excel 保存・読み込みを標準サポートしています。

#### [3] Node.js 系: ExcelJS vs nodeosbxl
| 行数（データ規模） | ExcelJS (相手方) | nodeosbxl (True) | nodeosbxl (False) | 高速化倍率 (対 ExcelJS) |
| :--- | :---: | :---: | :---: | :---: |
| **500 行** | 0.025s | **0.008s** | 0.011s | **3.34 倍 高速** |
| **1,000 行** | 0.039s | **0.010s** | 0.017s | **3.81 倍 高速** |
| **5,000 行** | 0.136s | **0.030s** | 0.075s | **4.47 倍 高速** |
| **10,000 行** | 0.230s | **0.055s** | 0.156s | **4.20 倍 高速** |
| **50,000 行 (20万セル)** | 0.933s | **0.327s** | 0.991s | **2.86 倍 高速** |

* **V8 イベントループのブロック防止**: ExcelJS は V8 ヒープ上で大量のオブジェクトを生成するため GC スパイクでイベントループを阻害しがちですが、nodeosbxl は C++ ネイティブ層で直接 OpenXML へエンコードするため V8 ヒープを消費しません。
* **高度な機能の完備**: ExcelJS では非対応のピボットテーブル作成、構造化参照数式（テーブル名参照）の評価、AES 暗号化保存などを完備しています。

#### [4] Java 系: Apache POI (XSSF) vs osbxl (Java)
| 行数（データ規模） | Apache POI (相手方) | osbxl (True) | osbxl (False) | 高速化倍率 (対 POI) |
| :--- | :---: | :---: | :---: | :---: |
| **500 行** | 0.563s | **0.021s** | 0.028s | **26.81 倍 高速** |
| **1,000 行** | 0.628s | **0.027s** | 0.038s | **23.26 倍 高速** |
| **5,000 行** | 0.836s | **0.061s** | 0.120s | **13.70 倍 高速** |
| **10,000 行** | 1.255s | **0.095s** | 0.203s | **13.21 倍 高速** |
| **50,000 行 (20万セル)** | ❌ **OOM (ヒープ枯渇死)** | **0.447s** | 1.210s | **完走 (相手方OOM)** |

* **ヒープ枯渇（OutOfMemoryError）の根絶**: Apache POI (XSSF) は DOM 型の XMLBeans クラス構造をヒープ上に展開するため 50,000 行で `-Xmx256m` を使い果たし即死します。osbxl Java はオフヒープ（C++ ネイティブ領域）で管理されるため、JVM ヒープを数十MBに抑えたまま 0.55 秒で安全に完走します。
* **巨大スキーマクラス初期化遅延の解消**: POI は小規模帳票（500行）でも 0.69 秒かかる初期化ペナルティがありますが、osbxl Java は初期化オーバーヘッドが極小で 0.12 秒台で即座に応答します。
* **SXSSF のような制約のない完全な Excel 操作**: POI の省メモリ版 SXSSF は「過去の行に戻れない」「ピボットや一部数式に非対応」といった厳しい制限がありますが、osbxl は全機能を完全サポートしながら高速・省メモリを両立しています。

## 5. アーキテクチャ考察：なぜ既存 OSS は落ち、osbxl は落ちないのか？

### ① 既存 OSS の限界：「言語ヒープ上のオブジェクト爆発」

PhpSpreadsheet、Apache POI (XSSF)、ExcelJS は、**「セル 1 つひとつを言語ランタイムのオブジェクトとして生成」** します。
- 50,000行 × 4列 ＝ **200,000 個のセルオブジェクト**
- さらに各セルが持つフォント、罫線、スタイル、数式定義オブジェクトが芋づる式に生成
- 保存時には共有文字列（Shared String Table）のハッシュマップがメモリを肥大化

その結果、出力される `.xlsx` ファイル自体はたかだか 1.5MB〜2MB 程度にもかかわらず、PHP では 256MB、Java では 256MB のヒープを瞬時に使い果たして異常終了します。

### ② osbxl の解決策：C++ ネイティブコアと 2次元配列一括投入

osbxl（各言語バインディング）では、言語側のヒープにセルオブジェクトを大量生成しません。
```javascript
// Node.js (nodeosbxl) での一括投入例
ws.setRangeData("A2", data);        // 2次元配列を生ポインタ経由で C++ ネイティブ層へ一括転送
ws.setRangeFormulas("D2", formulas); // 数式も 2次元配列で一括投入
```
1. 2次元配列として渡された生データを、言語ランタイムから **即座に C++ ネイティブメモリへ引き渡す**。
2. 最適化された C++ コアがストリーム処理で直接 OpenXML（ZIP / deflate）へ高速エンコード。
3. そのため、**Node.js の V8 ヒープは 20MB、Python ヒープは 28MB、PHP メモリは 32MB** のまま変動せず、言語ランタイムの OOM（ヒープ枯渇）クラッシュを根本から防止します。

### ③ サーバーサイドでの数式評価と SPILL（動的配列）対応

多くの OSS ライブラリ（openpyxl, ExcelJS）は数式文字列を書き込むことはできても、Excel 本体の計算機能を持たないため、サーバー上で数式結果（`SUM`, `VLOOKUP`, `XLOOKUP`）を取得できません。  
一方、**osbxl は「SPILL（スピル / 動的配列）形式の関数結果」に完全対応した最新の計算エンジン（約500関数）を内蔵**しています。Excel がインストールされていない Linux コンテナ環境でも、正確な計算結果を瞬時に取得可能です。

## 6. 導入推奨シナリオ

| シナリオ | 従来の課題 | osbxl 導入による効果 |
| :--- | :--- | :--- |
| **Web 帳票ダウンロード (100〜1,000行)** | 初期化遅延（POI は 0.5秒以上）、言語ごとの作法差 | **Java 4〜6倍、PHP 12〜14倍高速**。<br>全言語 0.01秒台で即時レスポンス。 |
| **月次バッチ・全件エクスポート (50,000行)** | メモリ上限超過（OOM）でプロセス強制終了 | **PHP・Java ともに 0.7秒〜0.9秒で安全完走**。<br>コンテナメモリ上限を気にする必要なし。 |
| **クラウドサーバー選定 (C3 vs C4)** | バッチ処理の短縮、同時接続耐性の向上 | **C4 を選択することで全言語 約1.1〜1.5倍のスループット向上** を享受。 |
| **マルチ言語・マイクロサービス開発** | 言語ごとに別ライブラリ・別構文 | **Java / Python / Node / PHP / WASM で 100% 同一 API**。 |
