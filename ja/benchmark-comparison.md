# Excelライブラリ 総合機能比較 ＆ 性能ベンチマーク実測レポート

[English Version (benchmark-comparison.md)](../en/benchmark-comparison.md) | [サンプル集トップ (index.md)](index.md)

本ドキュメントは、**osbxl**（Java / Python / Node.js / PHP / WebAssembly）と主要オープンソース Excel ライブラリ（Apache POI、openpyxl、PhpSpreadsheet、ExcelJS / SheetJS）の**詳細な機能サポート範囲の対比**、および**実務標準（200行）から大規模（50,000行）までの実測性能ベンチマーク**をまとめた技術資料です。

## 2. 実務の標準規模「200行（800セル）」でのパフォーマンス実測

「業務システムで最も頻繁に作成・ダウンロードされる標準的な帳票データ（200行 × 4列 = 計800セル＋SUM総合計）」を同一開発機環境（Linux x86_64）で実測比較しました。

### 言語別・実測データ比較

| 言語 / 環境 | ライブラリ | 処理時間 (秒) | メモリ消費 (MB) | 特徴・評価 |
|---|---|:---:|:---:|---|
| **Java** (JDK 1.8) | Apache POI 5.2.5 (XSSF)<br>**osbxl (Java)** | 0.622 秒<br>**0.139 秒** | 15.19 MB<br>**16.87 MB** | **osbxl が約 4.5 倍高速**。<br>POIはスキーマクラス群の初期化が重く、200行規模では osbxl の起動の軽さが圧倒的。 |
| **Node.js** (v24) | ExcelJS 4.4.0<br>**nodeosbxl** | 0.059 秒<br>**0.054 秒** | 113.48 MB<br>**132.02 MB** | **nodeosbxl が僅差で高速**（0.05秒台）。<br>V8ヒープ内ですぐに完了。nodeosbxlは計算エンジン内蔵ながら同等以上の速度。 |
| **Python** (3.14) | openpyxl 3.1.5<br>**pyosbxl** | **0.019 秒**<br>0.052 秒 | 53.57 MB<br>77.81 MB | openpyxlが最速だが**数式計算不可（セル値がNone）**。<br>pyosbxlは0.05秒で四則演算・SUMのネイティブ計算結果まで完了。 |
| **PHP** (8.5) | PhpSpreadsheet 5.10.0<br>**phposbxl** | 0.117 秒<br>**0.122 秒** | 26.00 MB<br>**2.00 MB** | 処理時間は0.1秒台で互角だが、**メモリは phposbxl が 13 倍省メモリ（2MB）**。<br>Webサーバーでの並行ダウンロード時に致命的な差となる。 |

## 3. 大規模データ限界負荷テスト（50,000行 / 200,000セル）

明細行数を **50,000 行（200,000 セル）** まで増やした際、既存ライブラリが直面するメモリ枯渇の瞬間と osbxl の完走データです。

### 50,000行 実測データ一覧

| 言語 / 環境 | ライブラリ | 処理時間 (秒) | メモリ消費 (MB) | 実測結果・限界検証 |
|---|---|:---:|:---:|---|
| **PHP** (8.5 / 128M) | PhpSpreadsheet 5.10.0<br>**phposbxl** | ✕ クラッシュ<br>**8.329 秒** | ✕ 128MB上限超過 (OOM)<br>**22.01 MB** | **PhpSpreadsheet はメモリ上限超過で即死**（`Fatal error: Allowed memory size exhausted`）。<br>**phposbxl はわずか 22MB で安全完走**（ファイルサイズ 1.93MB）。 |
| **Java** (JDK 1.8 / 256M) | Apache POI 5.2.5 (XSSF)<br>**osbxl (Java)** | ✕ クラッシュ<br>**15.740 秒** | ✕ 256MBヒープ枯渇 (OOM)<br>**42.13 MB** | **POI はヒープ枯渇で即死**（`OutOfMemoryError: Java heap space`）。<br>**osbxl は 42MB の軽量ヒープで完走**（SXSSFのような機能制限書き換え不要）。 |
| **Node.js** (v24) | ExcelJS 4.4.0<br>**nodeosbxl** | 1.379 秒<br>**7.836 秒** | 864.66 MB<br>**1,060 MB**<br>(*Nodeヒープは31MB) | ExcelJSは高速ストリーム出力可能だが**数式計算エンジン非搭載**。<br>nodeosbxlは**全数式のネイティブ計算（依存関係グラフ展開）を完結**して出力。 |
| **Python** (3.14) | openpyxl 3.1.5<br>**pyosbxl** | 2.529 秒<br>**8.049 秒** | 299.72 MB<br>**964 MB** | openpyxlは速いが**数式評価結果がすべて None**（Excel非起動下で値取得不可）。<br>pyosbxlは**ヘッドレス計算結果を保持**して完走。 |

> ※ **nodeosbxl / pyosbxl のメモリ特性について**:
> nodeosbxl と pyosbxl は、Excel非起動下で約500関数の数式を即時評価するため、C++ネイティブメモリ上に20万セル規模の「計算依存関係グラフ」を展開します。そのため約950〜1,060MBのRSSを消費しますが、ランタイム言語側のヒープ消費はNode.jsでわずか31.5MBに抑えられています。数式計算機能を持たない単なるシリアライザー（ExcelJS / openpyxl）とはアーキテクチャが異なります。

### 既存オープンソースライブラリの限界詳細

- **PhpSpreadsheet (PHP 8.5)**:
  `Fatal error: Allowed memory size of 134217728 bytes exhausted`
  &rarr; 128MB の PHP メモリ上限を突破し、StringTable 生成中にクラッシュ（即死）。
- **Apache POI (Java JDK 1.8)**:
  `java.lang.OutOfMemoryError: Java heap space`
  &rarr; 256MB ヒープ環境でクラッシュ。ストリーミング専用 `SXSSF` への大幅なコード書換が必要（読み戻し不可等の制約多）。

## 4. 各オープンソースライブラリの「決定的な弱点・限界」まとめ

### 1. openpyxl (Python)
- **最大の弱点**: **「ヘッドレス環境での数式評価が一切できない」**。
  - Excelで開かない限りセル値が `None` のままとなるため、Python側で「計算結果をAPIで返却する」「集計値バリデーションを行う」といった処理ができない。
  - パスワード暗号化エクスポートができない（msoffcrypto等の別ツールが必要）。

### 2. PhpSpreadsheet (PHP)
- **最大の弱点**: **「極端なメモリ消費とピボットテーブル・暗号化の非対応」**。
  - 200行でも26MB消費し、数万行で確実に `Allowed memory size exhausted` になる。
  - ピボットテーブルの生成に非対応。パスワード保護エクセルも自前では作成・復号できない。

### 3. Apache POI (Java)
- **最大の弱点**: **「大規模データ時のヒープ爆発（OOM）とSXSSFの機能制約」**。
  - 通常の `XSSFWorkbook` は256MBヒープ環境では5万行でクラッシュする。
  - ストリーミング版 `SXSSF` に逃げると、読み戻しやランダム書き換え、構造化参照などの高度なExcel機能が封殺される。

### 4. ExcelJS / SheetJS (Node.js)
- **最大の弱点**: **「ピボットテーブル・高度なチャート・数式エンジンの欠如」**。
  - 無償版では数式評価エンジンが存在せず、単なるデータ・スタイルのシリアライザーにとどまる。
  - ブラウザとバックエンドで一貫した高機能Excelエンジンを動かす手段がない（osbxlはWasm版で完全同期）。

## 5. 結論：osbxl のポジショニング

1. **200行の日常ユース**:
   - Javaでは約4.5倍高速、PHPでは13倍省メモリ、全言語で0.05〜0.1秒台の超軽快レスポンス。
2. **機能面での絶対優位**:
   - **「約500関数のヘッドレス計算」**
   - **「構造化参照・ピボットテーブル・2D/3Dチャート」**
   - **「パスワード暗号化/復号の標準ビルトイン」**
   - 上記を「どの言語でも同じAPIで扱える」ライブラリは、現行のオープンソース界隈には他に存在しません。
