## はじめに

業務システムや Web アプリケーション開発において、避けて通れない要件のひとつが**「Excel（.xlsx）の帳票出力・一括ダウンロード機能」**です。

各言語には古くからデファクトスタンダードとして使われている優秀なオープンソースライブラリが存在します：
- **Java**: Apache POI
- **Python**: openpyxl
- **Node.js**: ExcelJS
- **PHP**: PhpSpreadsheet

しかし、システムが成長してデータ量が増えたり、月次バッチや同時ダウンロードが発生した際、次のような**「Excel ライブラリの壁」**にぶつかった経験はないでしょうか？

- **「実務の数百行程度の帳票なのに、初期化やオブジェクト生成が重くてレスポンスに待たされる」**
- **「数万行規模の明細を出力しようとした瞬間、`OutOfMemoryError` や `Allowed memory size exhausted` でプロセスがクラッシュする」**
- **「openpyxl や ExcelJS は Excel 本体の計算エンジンがないため、サーバー上で数式（`SUM`, `VLOOKUP` など）の計算結果を取得できない」**
- **「Apache POI や既存 OSS の数式 Evaluator は、現代の実務で必須の新しい Excel 関数（`XLOOKUP`, `LET`, `LAMBDA`, `FILTER`, `UNIQUE` など）が実装されておらずエラーになる」**

今回は、C++ ネイティブコアを持ち、5 言語（Java / Python / Node.js / PHP / WebAssembly）に同一 API を提供する高速 Excel ライブラリ**「osbxl」**と、各言語の代表的 OSS ライブラリを同一環境下で比較実測しました。

- **GitHub サンプル集**: [https://github.com/osb-office/osbxl-samples](https://github.com/osb-office/osbxl-samples)
- **osbxl 公式サイト**: [https://osb-office.com/](https://osb-office.com/)
- **機能比較・詳細レポート**: [https://osb-office.com/pages/comparison.php](https://osb-office.com/pages/comparison.php)

## 1. 総合機能比較：何ができて、何ができないのか？

まず、各ライブラリのサポート範囲の全体像を整理します。

| カテゴリ | 機能項目 | osbxl (5言語共通) | Apache POI (Java) | openpyxl (Python) | PhpSpreadsheet (PHP) | ExcelJS (Node.js) |
|---|---|:---:|:---:|:---:|:---:|:---:|
| **入出力・安定性** | .xlsx / .xlsm / .xltx の読み込み・保存 | **◎** | **◎** | **◎** | **◎** | **◎** |
| | 大容量時の安定性 | **◎ (省メモリ完走)** | **△ (OOM 多発)** | **△ (行数比例で遅延)** | **✕ (128Mで即死)** | **◯ / △ (ヒープ圧迫)** |
| **数式計算** | 数式書き込み | **◎** | **◎** | **◎** | **◎** | **◎** |
| | **サーバーサイド数式評価**<br>(Excel非インストール環境での値計算) | **◎ 約500関数**<br>(XLOOKUP, VLOOKUP等) | **◯ 約300〜400関数**<br>(Evaluator搭載) | **✕ 非対応**<br>(開くまでセル値は None) | **△ 一部のみ**<br>(複雑関数未対応・極めて重い) | **✕ 非対応** |
| | **構造化参照数式**<br>(例: `SUM(Table[列名])`) | **◎ ネイティブ即時計算** | **△ (計算不可・保存のみ)** | **✕ 評価不可** | **✕ 評価不可** | **✕ 評価不可** |
| **データ表現** | テーブル作成 (`ListObject`) | **◎ (集計行付き)** | **◯ (低レイヤXML)** | **◯** | **◯** | **◯** |
| | オートフィルター・抽出判定 | **◎ 高速判定** | **◯** | **△ (手動判定要)** | **△** | **✕ (範囲設定のみ)** |
| | ピボットテーブル作成 | **◎ (`PivotTable`)** | **◯ (低レイヤXML)** | **△ (作成は限定的)** | **✕ 非対応** | **✕ 非対応** |
| | グラフ・チャート作成 | **◎ 2D/3D 多数対応** | **◯ (XDDF経由)** | **◯** | **△ (描画制約多)** | **✕〜△ (限定的)** |
| **セキュリティ** | パスワード暗号化保存 / 解除 | **◎ (標準サポート)** | **◯** | **✕ (サードパーティ要)** | **✕ (サードパーティ要)** | **✕ 非対応** |
| **開発体験** | マルチ言語同一 API | **◎ 5言語 100%同一** | **✕ (Java専用)** | **✕ (Python専用)** | **✕ (PHP専用)** | **✕ (JS専用)** |

特筆すべきは、**サーバーサイドでの数式計算能力**です。  
- openpyxl や ExcelJS は数式文字列を書き込むことはできても、その計算結果をサーバー側で即座に取得（`getValue`）することができません。
- Apache POI や PhpSpreadsheet は数式 Evaluator を持っていますが、評価できる関数が古く、**現代の Excel 実務で主流となっている `XLOOKUP`、`LET`、`LAMBDA`、`FILTER`、`UNIQUE` などの新しい関数は未実装（未サポート）** でエラーとなります。
- 一方、**osbxl は「SPILL（スピル / 動的配列）形式の関数結果」に完全対応した最新の計算エンジンを内蔵**しています。  
  `FILTER` や `UNIQUE`、`SEQUENCE` などのように、**1つの数式から隣接セルへ動的に結果がスピル（展開）される現代の Excel 計算モデルをそのまま評価可能**です。約 500 種類の関数群やテーブルの構造化参照を含め、Excel がインストールされていない Linux/コンテナ環境でも即座に高精度な計算結果を取得できます。

## 2. 実務の標準規模「200行（800セル）」での実測比較

多くの業務システムで最も頻繁にリクエストされるのが、「数ページ〜数十ページ程度の明細一覧をサッとダウンロードする」処理です。  
ここでは **200行 × 4列（商品ID、単価、数量、小計数式 ＝ 計800セル ＋ 総合計SUM）** の標準的な売上明細を生成した際の実測値を比較しました。

### 実測結果（Linux x86_64 環境）

| 言語 / 環境 | ライブラリ | 処理時間 (秒) | メモリ消費 (MB) | 実測のポイント |
|---|---|:---:|:---:|---|
| **Java** (JDK 1.8) | Apache POI 5.2.5 (XSSF)<br>**osbxl (Java)** | 0.652 秒<br>**0.105 秒** | 15.11 MB<br>**16.86 MB** | **osbxl が約 6.2 倍高速**。<br>POI は初期化やスキーマクラス群のロードが重く、小〜中規模では osbxl の起動速度が圧倒的。 |
| **Node.js** (v24) | ExcelJS 4.4.0<br>**nodeosbxl** (`setOnlyMode`) | 0.056 秒<br>**0.016 秒** | 103.95 MB<br>**121.14 MB** | **nodeosbxl が約 3.5 倍高速（わずか 16ms）**。<br>非同期イベントループを止めることなく一瞬でレスポンス可能。 |
| **Python** (3.14) | openpyxl 3.1.5<br>**pyosbxl** (`setOnlyMode`) | 0.017 秒<br>**0.016 秒** | 53.20 MB<br>**69.91 MB** | openpyxl を上回る **0.016 秒** をマーク。<br>Python ヒープ消費はわずか 12MB 程度。 |
| **PHP** (8.5) | PhpSpreadsheet 5.10.0<br>**phposbxl** | 0.073 秒<br>**0.024 秒** | 26.00 MB<br>**2.00 MB** | **phposbxl が約 3 倍高速 ＆ 13 倍省メモリ（2MB）**。<br>PHP-FPM での並行リクエスト時に決定的な差を生み出す。 |

### 考察：なぜ小規模でもこれほど差が出るのか？
Java の Apache POI は巨大な XML Beans やスキーマ構造の初期化に数百ミリ秒を要します。一方 osbxl は、最適化された C++ バイナリが直接バッファを組み立てるため、**Web API のレスポンスタイムとして体感できるレベルで高速（0.01〜0.1秒台）** に処理を完了します。

## 3. 大規模データ限界負荷テスト（50,000行 / 200,000セル）

次に、月次バッチや全件エクスポートを想定し、**50,000行 × 4列（計200,000セル）** の限界負荷テストを実施しました。  
コンテナ環境や一般的なサーバーで設定されるメモリ制限下で、既存ライブラリが直面する限界と osbxl の完走データです。

### 50,000行 実測データ一覧

| 言語 / 環境 | ライブラリ | 処理時間 (秒) | メモリ消費 (MB) | 実測結果・限界の状況 |
|---|---|:---:|:---:|---|
| **PHP** (8.5 / 128M上限) | PhpSpreadsheet 5.10.0<br>**phposbxl** | ❌ **クラッシュ (OOM)**<br>**5.836 秒** | ❌ **128MB上限超過**<br>**32.00 MB** | **PhpSpreadsheet は 128MB を超えて即死**。<br>`Fatal error: Allowed memory size exhausted`<br>**phposbxl はわずか 32MB で安全完走**（ファイルサイズ 1.93MB）。 |
| **Java** (JDK 1.8 / 256M上限) | Apache POI 5.2.5 (XSSF)<br>**osbxl (Java)** | ❌ **クラッシュ (OOM)**<br>**6.394 秒** | ❌ **256MBヒープ枯渇**<br>**36.19 MB** | **POI はヒープ枯渇でクラッシュ**。<br>`java.lang.OutOfMemoryError: Java heap space`<br>**osbxl は 36MB の軽量ヒープ・6.39秒で安全完走**。 |
| **Node.js** (v24) | ExcelJS 4.4.0<br>**nodeosbxl** (`setOnlyMode`) | 1.218 秒<br>**1.798 秒** | 772.11 MB<br>**1,836 MB**<br>*(V8ヒープ: 20.9MB)* | 同等の高速書き出しモードで **1.79 秒** を達成。<br>ExcelJS が V8 ヒープを大量消費するのに対し、**nodeosbxl の V8 ヒープ消費はわずか 20.9MB**。 |
| **Python** (3.14) | openpyxl 3.1.5<br>**pyosbxl** (`setOnlyMode`) | 2.500 秒<br>**1.900 秒** | 377.93 MB<br>**1,445 MB**<br>*(Pythonヒープ: 28MB)* | openpyxl（2.50秒）を上回る **1.90 秒** を達成。<br>**Python 側のヒープ消費はわずか 28MB** に抑えられ安定。 |

> 💡 **注釈：Node.js / Python で osbxl に `setOnlyMode` を適用した理由と背景**  
> - **比較相手の制約（数式エンジン非搭載）**:  
>   比較対象である **openpyxl** や **ExcelJS** には、サーバー側で数式を実際に評価・計算するエンジン自体が実装されていません（数式文字列をファイルにそのまま書き込むだけの「書き出し専用」動作です）。  
> - **公平なベンチマーク条件の統一**:  
>   osbxl は通常モードでは数式が設定されるたびに内蔵エンジンがリアルタイムに即時再計算を行いますが、これでは「数式計算を全く行わないオープンソース側」と「全セルを高精度にリアルタイム再計算している osbxl」で処理内容の不公平が生じます。  
> - **純粋な書き出し速度の比較**:  
>   そのため、openpyxl / ExcelJS と同等の**「数式のセットだけして、計算しないモード（`setOnlyMode = True`）」**をセットして実測しています。条件を揃えた場合、osbxl（C++ コア）は純粋な書き出し・XML 生成速度においても既存 OSS を圧倒するパフォーマンスを発揮します。
> - **生成されたファイルの挙動（Windows等 Excel での自動計算）**:  
>   なお、`setOnlyMode` をセットして作成した場合、スクリプト実行中のリアルタイムな計算結果（`getValue()`）はその場では取得できませんが、**保存された `.xlsx` ファイルを後から Windows 等の Excel で開くと、Excel 本体の計算機能によってすべての数式が通常通り自動計算・表示**されます。そのため、「サーバー側で計算結果を読む必要はなく、ユーザーにダウンロードさせる帳票を最速で出力したい」という実務ユースケースにおいて極めて有効なモードです。

## 4. なぜ既存 OSS は落ち、osbxl は落ちないのか？

### ① 既存 OSS の弱点：言語ヒープ上の「オブジェクト爆発」
PhpSpreadsheet や Apache POI (XSSF)、ExcelJS は、**「セル 1 つひとつを言語ランタイムのオブジェクトとして生成」** します。
- 50,000行 × 4列 ＝ **200,000 個のオブジェクト**
- さらに各セルが持つフォント、罫線、スタイル、数式定義オブジェクトが芋づる式に生成
- 保存時には共有文字列（Shared String Table）のハッシュマップがメモリを肥大化

その結果、出力される .xlsx ファイル自体はたかだか 2MB 程度にもかかわらず、PHP では 128MB、Java では 256MB のヒープを瞬時に使い果たして異常終了します。  
※ Apache POI にはディスクスワップを使う `SXSSF` もありますが、読み戻し不可、シート保護や一部数式・テーブル機能に厳しい制約がつきます。

### ② osbxl のアプローチ：C++ ネイティブコアと 2次元配列一括投入
osbxl（各言語バインディング）では、言語側のヒープに大量のセルオブジェクトを作りません。
```python
# pyosbxl での高速一括投入例
ws.setRangeData("A1", data)        # 2次元配列を一撃で C++ ネイティブ層へ
ws.setRangeFormulas("D2", formulas) # 数式も 2次元配列で一括投入
```
1. 2次元配列として渡された生データを、言語ランタイムから **即座に C++ ネイティブメモリへ引き渡す**。
2. C++ コアがストリーム処理で直接 OpenXML（ZIP）へ高速エンコード。
3. そのため、**Node.js の V8 ヒープは 20.9MB、Python ヒープは 28MB、PHP メモリは 32MB** のまま変動せず、ランタイムのメモリリミットによる OOM クラッシュを根本から防止します。

## 5. まとめ

| シーン | 従来の課題 | osbxl による解決 |
|---|---|---|
| **日常のWeb帳票 (200行)** | 初期化遅延、ライブラリごとの作法の違い | **Java 約6.2倍、PHP 約3倍高速**。<br>全言語 0.01〜0.1秒台で即時レスポンス。 |
| **大規模・バッチ (50,000行)** | メモリ上限超過（OOM）でプロセス即死 | **PHP 32MB、Java 36MB で安全完走**。<br>言語ヒープを枯渇させない堅牢性。 |
| **サーバー側数式評価** | openpyxl や ExcelJS は計算不可（None）<br>既存 OSS は XLOOKUP や SPILL に非対応 | **約 500 関数の計算エンジン内蔵**。<br>XLOOKUP・SPILL（動的配列）・構造化参照を即座にネイティブ評価。 |
| **マルチ言語開発** | 言語ごとに別々のライブラリ・別コード | **Java / Python / Node / PHP / WASM で 100% 同一 API**。 |

Excel 出力機能でパフォーマンスやメモリ不足、数式評価の制約に直面した際は、ぜひ選択肢のひとつとして検証してみてください。
